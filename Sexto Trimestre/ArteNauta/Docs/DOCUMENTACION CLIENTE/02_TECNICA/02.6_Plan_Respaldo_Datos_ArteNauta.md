## 1. OBJETIVO Y ALCANCE

### 1.1 Objetivo
Proteger la información de ArteNauta (cuentas, portafolios, publicaciones y comisiones) y definir los pasos exactos para recuperarla ante borrados accidentales, daños en datos, pérdida total de la base de datos o fallos de despliegue, dentro de tiempos acordados.

### 1.2 RPO y RTO

| Indicador | Valor propuesto | Justificación |
|-----------|-----------------|---------------|
| **RPO** (datos que se pueden perder) | **24 horas** | Un artista que pierda un día de cambios en su portafolio puede rehacerlos. Una comisión es más sensible, pero con pocos movimientos por día un RPO diario es razonable en esta etapa. |
| **RTO** (tiempo máximo de caída) | **4 horas** | Es una plataforma de portafolios y encargos, no un sistema transaccional crítico; media jornada de caída es tolerable. |
| **Disponibilidad objetivo** | 99 % mensual [VERIFICAR] | ≈ 7 horas de caída permitidas al mes. |


### 1.3 Alcance

| Incluido ✅ | Excluido ❌ |
|------------|-------------|
| Base de datos PostgreSQL en Supabase | Equipos personales de los usuarios |
| Estructura: tablas, índices, triggers, funciones, políticas RLS | Disponibilidad de Supabase/Vercel como infraestructura (es del proveedor) |
| contenido sensible almacenado en la base de datos| Datos de terceros (correo, pasarela de pagos (Futuro)) |
| Código fuente (versionado en GitHub) | Registros de navegación o analítica |
| Configuración y variables de entorno (guardadas en un gestor seguro, nunca en el repo) | |

## 2. POLÍTICA DE RESPALDOS

### 2.1 Regla 3-2-1

```
3 copias    → Producción (Supabase) + backup local (.dump) + copia fuera del sitio
2 medios    → Supabase (nube) + disco del responsable
1 fuera     → Google Drive u otro proveedor distinto a Supabase  [COMPLETAR cuál]
```

| Copia | Dónde está | Estado |
|-------|-----------|--------|
| Original | Supabase (producción) | Activa |
| Copia 1 | Disco del responsable técnico (`~/backups/artenauta`) | Activa |
| Copia 2 | cifrado de manera local y fuera del repositorio | Activa |

### 2.2 Criticidad de los datos

| Nivel | Tablas / datos | Si se pierde... | RPO | RTO | Retención |
|-------|----------------|-----------------|-----|-----|-----------|
| 🔴 **Crítico** | `usuarios` (credenciales, roles), `perfiles` | Se pierden cuentas y acuerdos entre clientes y artistas; riesgo de conflicto y de reputación | 24 h | 4 h | 90 días de diarios + mensuales 12 meses |
| 🟡 **Importante** | `publicaciones`, imágenes de las obras | El trabajo de los artistas desaparece; se puede reconstruir solo si ellos conservan sus archivos | 24 h | 8 h | 30 días de diarios + mensuales 6 meses |
| 🟢 **Normal** | `categorias`, `roles`, `mensajes`,`conversaciones`  | Se reconstruyen con el script de datos iniciales | 24 h | 24 h | 30 días |

> **[VERIFICAR]** Ajusta la lista a las tablas reales de tu Supabase.

### 2.3 Responsabilidad compartida

| Componente | Quién protege | Qué hace el equipo | Verificación |
|------------|---------------|--------------------|--------------|
| Infraestructura de Supabase y Vercel | Proveedor | Elegir plan adecuado | Mensual: revisar estado y plan |
| Backups automáticos de Supabase | Proveedor (según plan, ver 5.3) | Comprobar en el panel que existen | Mensual |
| Datos de la base (borrados por error, datos dañados) | **Equipo ArteNauta** | Backup propio + pruebas de restauración | Semanal (integridad) y mensual (restauración) |
| Archivos en Storage | **Equipo ArteNauta** | Copia independiente (Sección 6.4) | Mensual |
| Código | GitHub | Commits frecuentes, ramas protegidas | Cada despliegue |
| Claves y secretos | **Equipo ArteNauta** | Gestor de contraseñas; copia del `JWT_SECRET` | Trimestral |

> Aunque Supabase tenga infraestructura sólida, **si alguien borra una tabla por error, Supabase no lo deshace por nosotros** si no tenemos una copia útil.

### 2.4 Retención legal y protección de datos
- ArteNauta, en su estado actual, **no procesa pagos ni emite facturas**, por lo que no aplica retención contable. Si se integra una pasarela de pagos **(Futuro)**, habrá que revisar los plazos legales de conservación de documentos comerciales en Colombia.
- La base contiene **datos personales** (nombre, correo, hash de contraseña). En Colombia aplica la Ley 1581 de 2012 de protección de datos personales. Por eso los backups se tratan como datos sensibles: cifrados en la copia externa, nunca en GitHub.

## 3. ESTRATEGIA DE RESPALDO

```
NIVEL 1 ── Backups de Supabase (automáticos, según plan)
   │        Frecuencia: diaria | Retención: según plan | Recuperación: ~1 h
   │        Protege contra: errores y fallos recientes
   ▼
NIVEL 2 ── Backup propio con pg_dump (script + cron)
   │        Frecuencia: diaria, 2:00 a.m. | Retención: 30 días + mensuales
   │        Recuperación: ~1-2 h | Protege contra: pérdida del proyecto Supabase
   ▼
NIVEL 3 ── Copia fuera del sitio (Google Drive u otro)
   │        Frecuencia: semanal | Retención: 12 semanas + mensuales
   │        Recuperación: ~2-4 h | Protege contra: cuenta comprometida, ransomware
   ▼
NIVEL 4 ── Código en GitHub (control de versiones)
            Frecuencia: cada push | Retención: ilimitada | Recuperación: minutos
            Protege el CÓDIGO, no los datos
```

| Nivel | Qué respalda | Frecuencia | Retención | Dónde | Recuperación |
|-------|--------------|-----------|-----------|-------|--------------|
| 1 | Base completa (snapshot) | Diaria | Según plan (5.3) | Supabase | ~1 h |
| 2 | Esquema `public` (estructura + datos) | Diaria | 30 días + mensuales | Disco local | 1-2 h |
| 3 | Copia del nivel 2 + Storage | Semanal | 12 semanas + mensuales | Nube externa | 2-4 h |
| 4 | Código fuente | Cada push | Ilimitada | GitHub | Minutos |

**GitHub no es un backup de datos.** Guarda el código; no guarda los usuarios, publicaciones ni demas informacion que viven en la base de datos. Si el proyecto de Supabase se pierde, el código se recupera pero los datos no.

## 4. TIPOS DE RESPALDO

| Tipo | ¿Lo usamos? | Justificación |
|------|-------------|---------------|
| **Completo lógico** (`pg_dump -Fc`) | ✅ Sí, base de la estrategia | La base es pequeña; un completo diario es rápido, se restaura por sí solo y es portable entre proyectos. |
| **Snapshot** (de Supabase) | ✅ Sí, Nivel 1 | Restauración rápida; depende del plan. |
| **Incremental / diferencial** | ❌ No por ahora | Con una base de pocos MB, un completo diario es más simple y fiable. Se reconsidera cuando el tamaño lo justifique **(Futuro)**. |
| **Físico / PITR** | ❌ No por ahora | Es de pago (Sección 12). Se evaluaría si el RPO debe bajar de 24 horas. |

**Qué incluye el backup completo:** `pg_dump --schema=public` exporta **estructura y datos**: tablas (`roles`, `usuarios`, `categorias`, `publicaciones`, `conversaciones`,`mensajes`), índices, triggers, funciones y políticas RLS.


**Diferencia incremental vs. diferencial (ejemplo):**
Lunes completo. *Incremental:* martes = cambios desde lunes, miércoles = cambios desde martes; restaurar el miércoles exige lunes + martes + miércoles. *Diferencial:* miércoles = cambios desde el lunes; restaurar exige lunes + miércoles. Si un día usáramos incrementales, un `created_at > último_backup` **no** detectaría registros modificados ni eliminados; harían falta una columna `updated_at` (ya la tienen nuestras tablas por el trigger) y una tabla de borrados o *soft delete* (`activo = false`).

Para el plan gratuito, la misma documentación **recomienda exportar los datos periódicamente con la CLI y mantener copias fuera del sitio**.

**Conclusión:** como el plan de Supabase puede no darnos un backup utilizable, el **Nivel 2 es obligatorio** y es el que sostiene el RPO de 24 horas.

## 6. PROCEDIMIENTOS DE RESPALDO 🧪

### 6.1 Prerrequisitos
- Cliente PostgreSQL instalado (`pg_dump`, `pg_restore`, `psql`) con versión **igual o mayor** a la de tu proyecto Supabase (*Project Settings → Infrastructure*).
- Cadena de conexión en variable de entorno (**nunca dentro del script**). En Supabase: **Connect → Session pooler** si tu red no tiene IPv6.
- `.gitignore` con `*.dump`, `*.sql`, `*.sha256` (opcional), `.env` y la carpeta de backups.

### 6.2 Laboratorio 1: primer backup manual [PROBAR]

```bash
export DB_URL="postgresql://postgres.[ref]:[CONTRASEÑA]@[host]:5432/postgres"

FECHA=$(date +%Y-%m-%d_%H-%M)
pg_dump "$DB_URL" --schema=public --no-owner -Fc -f "backup_$FECHA.dump"

# Huella (elige según tu sistema)
shasum -a 256 "backup_$FECHA.dump" > "backup_$FECHA.sha256"    # Mac
sha256sum   "backup_$FECHA.dump" > "backup_$FECHA.sha256"      # Linux

# Ver el contenido sin restaurar
pg_restore --list "backup_$FECHA.dump" | head -40
```

### 6.3 Script `backup.sh` (diario)

```bash
#!/usr/bin/env bash
# backup.sh - Backup diario de ArteNauta
# Requiere la variable de entorno DB_URL (no se escribe en este archivo).
set -euo pipefail

: "${DB_URL:?Falta la variable de entorno DB_URL}"

BACKUP_DIR="${BACKUP_DIR:-$HOME/backups/artenauta}"
RETENCION_DIAS=30
TAMANO_MINIMO=10240   # bytes: por debajo de esto el backup se considera sospechoso
LOG="$BACKUP_DIR/backup.log"

mkdir -p "$BACKUP_DIR"
log() { echo "$(date '+%Y-%m-%d %H:%M:%S') | $*" >> "$LOG"; }

huella() {
  if command -v sha256sum >/dev/null 2>&1; then sha256sum "$1"
  else shasum -a 256 "$1"; fi
}

FECHA=$(date +%Y-%m-%d_%H-%M)
ARCHIVO="backup_$FECHA.dump"
INICIO=$(date +%s)

log "INICIO backup $ARCHIVO"

if ! pg_dump "$DB_URL" --schema=public --no-owner -Fc -f "$BACKUP_DIR/$ARCHIVO"; then
  log "ERROR pg_dump falló"
  rm -f "$BACKUP_DIR/$ARCHIVO"
  exit 1
fi

TAMANO=$(wc -c < "$BACKUP_DIR/$ARCHIVO" | tr -d ' ')
if [ "$TAMANO" -lt "$TAMANO_MINIMO" ]; then
  log "ERROR backup demasiado pequeño ($TAMANO bytes), posible backup vacío"
  exit 1
fi

# Verifica que el archivo sea legible
pg_restore --list "$BACKUP_DIR/$ARCHIVO" > /dev/null

# Huella (se guarda con ruta relativa para poder verificarla en la misma carpeta)
( cd "$BACKUP_DIR" && huella "$ARCHIVO" > "$ARCHIVO.sha256" )

# Retención: borra diarios con más de RETENCION_DIAS días
find "$BACKUP_DIR" -name 'backup_*.dump'   -mtime +"$RETENCION_DIAS" -delete
find "$BACKUP_DIR" -name 'backup_*.sha256' -mtime +"$RETENCION_DIAS" -delete

DURACION=$(( $(date +%s) - INICIO ))
log "OK $ARCHIVO | $TAMANO bytes | ${DURACION}s"
```

Programación con cron (todos los días a las 2:00 a.m.):
```bash
# minuto hora día-mes mes día-semana  comando
0 2 * * * DB_URL="$(cat $HOME/.artenauta_db_url)" /ruta/a/backup.sh >> /ruta/a/backup.cron.log 2>&1
```
> El archivo `~/.artenauta_db_url` debe tener permisos `chmod 600`. En **Windows**, usa WSL con cron o el Programador de tareas ejecutando el script con Git Bash/WSL. **[COMPLETAR cuál usa el equipo]**

### 6.4 Copia fuera del sitio y archivos de Storage

**Base de datos (semanal, domingo):** copiar el último `.dump` y su `.sha256` a la nube externa.
```bash
# Ejemplo con rclone configurado hacia Google Drive (remoto "gdrive")  [PROBAR]
rclone copy "$BACKUP_DIR" gdrive:ArteNauta-backups --include "backup_*.dump" --include "backup_*.sha256" --max-age 8d
```

**Comprobación real de la copia externa:** descargar el archivo desde la nube a otra carpeta y comparar su huella con el `.sha256` original. Comparar el archivo local con un `.sha256` generado de ese mismo archivo local **no demuestra** que la copia en la nube esté bien.
```bash
rclone copy gdrive:ArteNauta-backups/backup_FECHA.dump /tmp/verificacion/
cd /tmp/verificacion && sha256sum -c backup_FECHA.dump.sha256    # o shasum -a 256 -c en Mac
```

**Archivos de Supabase Storage [VERIFICAR si se usa]:** `pg_dump` no copia los archivos. Se respaldan con la CLI de Supabase, con la API de Storage o con el protocolo S3 compatible que ofrece Supabase **[COMPLETAR el método elegido y probarlo]**.

**Secretos:** guardar `JWT_SECRET`, `SUPABASE_URL` y las claves en un gestor de contraseñas compartido por el equipo. Si se pierde el `JWT_SECRET`, las sesiones activas se invalidan (los usuarios deben iniciar sesión de nuevo).

### 6.5 Backup manual antes de un cambio riesgoso
Antes de modificar tablas, correr migraciones o hacer cargas masivas:
1. Ejecutar `./backup.sh` (o el comando de 6.2) y confirmar `OK` en el log.
2. Anotar en `control_backups` el motivo (p. ej. "antes de migración X").
3. Solo entonces ejecutar el cambio, preferiblemente primero en el proyecto de prueba.

## 7. PROCEDIMIENTOS DE RESTAURACIÓN 🧪

> **Regla:** nunca se restaura directo sobre producción sin haber verificado antes en un proyecto de prueba. Se mantiene un **segundo proyecto de Supabase** vacío para ese fin: `[COMPLETAR nombre/ref]`.

### 7.1 Laboratorio 2: restaura tu backup [PROBAR]

1. **Contar registros en producción** y guardar el resultado:
```sql
SELECT 'roles' AS tabla, COUNT(*) FROM roles
UNION ALL SELECT 'usuarios', COUNT(*) FROM usuarios
UNION ALL SELECT 'categorias', COUNT(*) FROM categorias
UNION ALL SELECT 'publicaciones', COUNT(*) FROM publicaciones
```

5. Detener el cronómetro → ese es el **RTO real** de este escenario.

### 7.2 Escenario 1: borrado accidental de un registro
**RPO:** 24 h · **RTO:** 1 h · **Complejidad:** baja
1. Identificar qué se borró, quién y cuándo (tabla, id, hora aproximada).
2. Tomar un backup manual del estado actual (6.5).
3. Restaurar el último backup bueno **en el proyecto de prueba** (7.1, pasos 2-3).
4. En la base de prueba, localizar la fila: `SELECT * FROM publicaciones WHERE id_publicacion = [ID];`
5. Reinsertar la fila en producción con un `INSERT` explícito (respetando las llaves foráneas: el artista y la categoría deben existir).
6. **Verificación:** consultar la fila en producción y pedir al artista que confirme que su obra aparece en la galería.

### 7.3 Escenario 2: tabla con datos dañados
**RPO:** 24 h · **RTO:** 2 h · **Complejidad:** media
1. Dejar de escribir en la tabla: pausar la funcionalidad o poner el backend en modo mantenimiento (la forma más segura es desde el backend, no desde políticas RLS).
2. Backup manual del estado actual (6.5).
3. Restaurar el último backup bueno en el proyecto de prueba.
4. Comparar las filas dañadas entre prueba y producción y **corregir por filas** con `UPDATE ... FROM` o `INSERT`.
5. **Verificación:** conteos, consultas de validación (8.6) y prueba funcional en la aplicación.

> ⚠️ **No usar `TRUNCATE ... CASCADE` ni `DELETE` masivo** sobre `publicaciones` o `usuarios`: por las llaves foráneas vaciaría o alteraría tablas relacionadas (`comisiones.id_publicacion` pasaría a `NULL` por `ON DELETE SET NULL`, y eliminar usuarios arrastra sus publicaciones por `CASCADE`). Además, una política RLS adicional `FOR ALL USING (false)` **no** funciona como "solo lectura": en PostgreSQL las políticas permisivas se combinan con **OR**, y `FOR ALL` incluiría también `SELECT`.

### 7.4 Escenario 3: se perdió toda la base de datos
**RPO:** 24 h · **RTO:** 4 h · **Complejidad:** alta
1. Declarar el desastre y activar el DRP (Sección 8).
2. Si el plan lo permite, intentar primero restaurar desde **Database → Backups** del panel de Supabase.
3. Si no es posible, crear un **nuevo proyecto de Supabase** (o usar el de prueba).
4. Restaurar el último `.dump` verificado en el proyecto nuevo (7.1, pasos 2-3).
5. Restaurar los archivos de Storage desde su copia (6.4) **[COMPLETAR]**.
6. Actualizar variables de entorno (`SUPABASE_URL`, clave de servicio) en el backend y en Vercel; **redesplegar**.
7. Conservar el mismo `JWT_SECRET` (desde el gestor de contraseñas) para no invalidar sesiones.
8. **Verificación:** conteos contra el último registro conocido, consultas de validación (8.6), inicio de sesión de un usuario de cada rol y carga de la galería.
9. Comunicar al cliente con la plantilla de 8.5.

### 7.5 Escenario 4: una actualización de la aplicación salió mal
**RPO:** 0 (los datos no se tocan salvo migraciones) · **RTO:** 30 min · **Complejidad:** baja
1. **Frontend en Vercel:** en el panel *Deployments*, promover/restaurar un despliegue anterior que funcionaba (rollback a nivel de despliegue). No aplican comandos de servidor tradicionales (`systemctl`, `nginx`) porque el frontend es *serverless*. **[PROBAR y capturar]**
2. **Backend:** si está en Vercel u otro servicio, aplicar el mismo mecanismo de despliegue anterior; si no, `git revert` del commit problemático y nuevo despliegue. **[COMPLETAR según dónde esté desplegado]**
3. **Si hubo cambio de base de datos (migración):** restaurar desde el backup manual tomado antes del cambio (6.5), siguiendo el Escenario 2 o 3 según el alcance.
4. **Verificación:** abrir la URL de producción, iniciar sesión y recorrer galería, perfil y edición de una publicación.

## 8. PLAN DE RECUPERACIÓN ANTE DESASTRES (DRP)

### 8.1 Qué es un desastre en ArteNauta
Cualquier evento que deje la plataforma fuera de servicio por **más de 4 horas** (el RTO), o que cause pérdida o exposición de datos de usuarios.

### 8.2 Causas probables

| # | Causa | Probabilidad | Impacto | Mitigación |
|---|-------|:------------:|:-------:|-----------|
| 1 | Borrado o modificación por error humano | Alta | Medio | Backups diarios, confirmaciones en la interfaz (SweetAlert2), soft delete |
| 2 | **Proyecto de Supabase pausado por inactividad** (plan gratuito) | Media | Alto | Mantener actividad, plan de pago antes de producción real, backup propio |
| 3 | Filtración de claves (`service_role`, `.env` en GitHub) | Media | Muy alto | `.gitignore`, rotar claves, revisar historial de Git |
| 4 | Despliegue o migración defectuosos | Media | Medio | Backup previo, rollback en Vercel, pruebas en proyecto de prueba |
| 5 | Cuenta comprometida o ransomware | Baja | Muy alto | Copia externa independiente, 2FA en Supabase, GitHub y Google |

### 8.3 Fases del DRP

| Fase | Acciones | Responsable | Tiempo objetivo |
|------|----------|-------------|-----------------|
| **1. Detección** | Alerta del monitoreo (Sección 10) o reporte de usuarios; confirmar el problema y su alcance | [COMPLETAR] | 0-15 min |
| **2. Activación y comunicación** | Declarar desastre, avisar al equipo y al cliente (plantilla 8.5) | [COMPLETAR] | 15-30 min |
| **3. Recuperación** | Ejecutar el escenario que corresponda (Sección 7) | [COMPLETAR] | 30 min - 3 h |
| **4. Validación** | Ejecutar consultas de 8.6, probar login por rol y flujos clave | [COMPLETAR] | 30 min |
| **5. Post-mortem** | Reunión sin buscar culpables; qué falló, qué funcionó y qué cambiar en el plan | Todo el equipo | Máx. 5 días hábiles |

### 8.4 Cuando la causa es una filtración de credenciales

### 8.6 Consultas de validación posteriores a una restauración

Todas usan llaves foráneas, no nombres:

```sql
-- 1. Conteos por tabla (comparar con los de antes del incidente)
SELECT 'usuarios' AS tabla, COUNT(*) FROM usuarios
UNION ALL SELECT 'publicaciones', COUNT(*) FROM publicaciones
UNION ALL SELECT 'comisiones', COUNT(*) FROM comisiones;

-- 2. Publicaciones huérfanas (sin artista válido) -> debe devolver 0 filas
SELECT p.id_publicacion
FROM publicaciones p
LEFT JOIN usuarios u ON u.id_usuario = p.id_usuario_artista
WHERE u.id_usuario IS NULL;

-- 3. Comisiones cuyo artista no tiene rol de artista -> debe devolver 0 filas
SELECT c.id_comision
FROM comisiones c
JOIN usuarios u ON u.id_usuario = c.id_usuario_artista
WHERE u.id_rol <> 2;

-- 4. Valores imposibles -> debe devolver 0 filas
SELECT id_publicacion FROM publicaciones WHERE precio < 0
UNION ALL
SELECT id_comision FROM comisiones WHERE precio_acordado < 0;

-- 5. Usuarios con rol inexistente -> debe devolver 0 filas
SELECT u.id_usuario
FROM usuarios u
LEFT JOIN roles r ON r.id_rol = u.id_rol
WHERE r.id_rol IS NULL;

-- 6. Estructura presente: triggers y políticas
SELECT COUNT(*) AS triggers FROM information_schema.triggers WHERE trigger_schema = 'public';
SELECT COUNT(*) AS politicas FROM pg_policies WHERE schemaname = 'public';
```
> **[VERIFICAR]** Algunas consultas dependen de las columnas de tu esquema real.

## 10. MONITOREO Y ALERTAS

El peor caso es la **falla silenciosa**: el backup "corre" pero genera archivos vacíos o incompletos. Por eso se vigila la **antigüedad** y el **tamaño**, no solo que el script se haya ejecutado.

### 10.1 Tabla de alertas

| Evento | Severidad | Acción | A quién se avisa |
|--------|-----------|--------|------------------|
| Último backup con más de 26 h de antigüedad | 🔴 Crítica | Ejecutar backup manual y revisar el cron | Responsable técnico y suplente |
| Backup con tamaño menor al mínimo | 🔴 Crítica | Revisar `backup.log`, la conexión y la versión de `pg_dump` | Responsable técnico |
| Falla del `pg_dump` en el log | 🟠 Alta | Reintentar y revisar credenciales | Responsable técnico |
| Espacio en disco por encima de 85 % | 🟡 Media | Limpiar copias antiguas o ampliar espacio | Responsable técnico |
| Copia externa semanal no realizada | 🟠 Alta | Subir manualmente y verificar huella | Responsable técnico |
| Proyecto Supabase en riesgo de pausa | 🟠 Alta | Generar actividad / revisar plan | Todo el equipo |

### 10.2 Script `verificar_backup.sh`

Funciona en Mac y Linux (usa `find` y `wc -c` en lugar de `stat`, cuyas opciones difieren entre sistemas):

```bash
#!/usr/bin/env bash
# verificar_backup.sh - Detecta backups viejos, vacíos o poco espacio.
BACKUP_DIR="${BACKUP_DIR:-$HOME/backups/artenauta}"
MAX_MINUTOS=$((26*60))     # 26 horas
TAMANO_MINIMO=10240        # bytes
USO_MAX=85                 # % de disco usado

alerta() { echo "🔴 ALERTA: $*"; ALERTAS=1; }
ALERTAS=0

ULTIMO=$(ls -t "$BACKUP_DIR"/backup_*.dump 2>/dev/null | head -1)
if [ -z "$ULTIMO" ]; then
  alerta "No existe ningún backup en $BACKUP_DIR"
else
  # ¿Es reciente? (find imprime el archivo solo si fue modificado dentro del límite)
  if [ -z "$(find "$ULTIMO" -mmin -"$MAX_MINUTOS")" ]; then
    alerta "El último backup es demasiado antiguo: $ULTIMO"
  fi
  # ¿Tiene un tamaño razonable?
  TAMANO=$(wc -c < "$ULTIMO" | tr -d ' ')
  if [ "$TAMANO" -lt "$TAMANO_MINIMO" ]; then
    alerta "Backup sospechosamente pequeño ($TAMANO bytes): $ULTIMO"
  fi
fi

# Porcentaje de disco USADO (no libre)
USO=$(df -P "$BACKUP_DIR" 2>/dev/null | awk 'NR==2 {gsub("%","",$5); print $5}')
if [ -n "$USO" ] && [ "$USO" -gt "$USO_MAX" ]; then
  alerta "Disco al ${USO}% de uso"
fi

[ "$ALERTAS" -eq 0 ] && echo "✅ Backups en orden: $ULTIMO"
exit "$ALERTAS"
```

**Prueba obligatoria [PROBAR]:** crea un archivo `.dump` vacío (`touch backup_prueba.dump`) o cambia `MAX_MINUTOS` a `1` y confirma que el script **dispara la alerta**. Pega aquí la captura.
