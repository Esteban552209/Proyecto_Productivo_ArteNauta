## 1. RESUMEN EJECUTIVO


**ArteNauta** es una aplicación web y móvil que conecta a artistas independientes y aprendices con clientes y entusiastas del arte. Permite publicar portafolios, explorar una galería con filtros por técnica y categoría, gestionar solicitudes de cambio de rol, recibir notificaciones en tiempo real de interacciones y comunicarse mediante un sistema de chat. Está pensada para la comunidad artística local e institucional, y nace como proyecto formativo con potencial comercial.


```
Paradigma:        SPA (Single Page Application) + App Móvil Flutter
Arquitectura:     Cliente-servidor en 3 capas (React + API Express + Supabase/PostgreSQL)
Tipo:             Aplicación cloud-based
Organización:     Monorepo (frontend y backend en un mismo repositorio)
Escalabilidad:    Horizontal automática según el plan del hosting
```


### Características principales
- Perfiles y portafolios de artistas con biografía y categorías artísticas.
- Galería de publicaciones (obras) con buscador y filtros.
- Gestión de roles: usuario/cliente, artista y administrador.
- Autenticación con sesión basada en token JWT.
- Sistema de notificaciones en tiempo real (likes, comentarios, mensajes, solicitudes de rol).
- Chat de mensajería entre usuarios.
- App móvil Flutter conectada al mismo backend Express.
- Interfaz responsiva.


### Principios de diseño
| Principio | Cómo se aplica en ArteNauta |
|-----------|-----------------------------|
| **Separation of Concerns** | El frontend solo presenta; la lógica y el acceso a datos viven en el backend Express. |
| **Security by Design** | El frontend nunca accede directo a Supabase: toda operación pasa por la API, que valida token y rol mediante `verificarToken`. |
| **API First** | Toda funcionalidad del sistema (web y móvil) consume los mismos endpoints del backend Express. |
| **Reutilización** | Hooks personalizados, componentes pequeños y servicios compartidos entre vistas. |

### ¿Por qué React + Vite?
1. **Componentes reutilizables:** perfiles, tarjetas de obra y formularios se repiten en varias vistas.
2. **Ecosistema amplio** (rutas, hooks, librerías de UI) y mucha documentación para un equipo en formación.
3. **Vite** ofrece arranque casi instantáneo y recarga rápida en desarrollo, con configuración mínima frente a Webpack.


### ¿Por qué Express como backend intermediario?
Una buena pratica de programacion y seguridad establece que el frontend no debe consultar Supabase (Backend) directamente. Express actúa como capa intermedia que:
1. Valida el token JWT antes de ejecutar cualquier operación (middleware `verificarToken`).
2. Centraliza la lógica de negocio (por ejemplo, notificar al admin al solicitar ser artista).
3. Permite agregar validaciones sin tocar el frontend ni el móvil.


### ¿Por qué Supabase?
1. **PostgreSQL real:** permite relaciones, índices, triggers y funciones SQL.
2. **Capa gratuita** suficiente para un proyecto académico.
3. **Panel con SQL Editor**, que acelera el desarrollo y las pruebas.


### Comparación: Supabase vs Firebase
| Criterio | Supabase | Firebase |
|----------|----------|----------|
| Modelo de datos | Relacional (SQL) | NoSQL (documentos) |
| Relaciones y JOIN | Nativos | Se simulan manualmente |
| Consultas complejas | Simples con SQL | Más limitadas |
| Código abierto | Sí | No |
| RLS nativo | Sí | Reglas de seguridad propias |


**Decisión:** ArteNauta tiene datos fuertemente relacionados (usuarios, publicaciones, categorías, notificaciones), por lo que un modelo relacional es más natural.

### 3.3 Flujo de datos: "Usuario solicita ser artista"


```
1. Usuario hace clic en "Solicitar ser Artista"
        │
        ▼
2. SolicitarArtista.jsx (web) / perfil_screen.dart (móvil)
   envía POST /notificaciones/solicitudes con token
        │
        ▼
3. verificarToken.js valida el JWT
   Si inválido → 401 Unauthorized
        │
        ▼
4. notificaciones.js verifica si ya hay solicitud pendiente
   en Supabase → tabla solicitudes
   Si existe → 400 "Ya tienes una solicitud pendiente"
        │
        ▼
5. Se inserta la solicitud en tabla solicitudes
   estado_solicitud = 'Pendiente'
        │
        ▼
6. Se consultan todos los admins (id_rol = 3)
   Se inserta notificación para cada admin
   tipo_notificacion = 'Informativo'
        │
        ▼
7. Admin ve el badge en la campanita → abre notificaciones
   → botones Aprobar / Rechazar
        │
        ▼
8. PATCH /notificaciones/solicitudes/:id/aprobar
   → estado = 'Aceptada'
   → id_rol del usuario cambia a 2 (Artista)
   → notificación al usuario: tipo_notificacion = 'solicitud_aprobada'
```


### 3.4 Flujo de datos: "Editar una publicación"


```
1. El artista pulsa "Editar" en una obra.
2. El componente envía PATCH al backend con el token en Authorization.
3. verificarToken valida el token y carga el usuario.
4. El middleware confirma que es artista (id_rol = 2) o admin (3).
5. El backend verifica que la publicación pertenezca al artista y ejecuta UPDATE en Supabase.
6. La API responde con la publicación actualizada.
7. El componente actualiza el estado de React y SweetAlert2 confirma la operación.
```

### 3.5 Estado global y sesión
- Al iniciar sesión, el backend devuelve un **token JWT** y los datos del usuario.
- El frontend web los guarda en `localStorage` con las claves `"token"` y `"usuario"`.
- La app móvil los guarda en `SharedPreferences`.
- Cada petición protegida envía el token en la cabecera `Authorization: Bearer <token>`.
- Al cerrar sesión se eliminan ambas claves.

**Decisiones de borrado (`ON DELETE`):**
- `publicaciones → usuarios` usa **CASCADE**: si se elimina un artista, sus obras dejan de tener sentido.
- `solicitudes → usuarios` usa **CASCADE**: las solicitudes pertenecen al usuario.
- `publicaciones → categorias` usa **SET NULL**: borrar una categoría no debe eliminar las obras.
- `notificaciones → usuarios` usa **CASCADE**: sin usuario no hay a quién notificar.
- Se prefiere **soft delete** (`estado_cuenta = false`) en usuarios.

```javascript
// Backend — notificaciones.js
router.get("/notificaciones", verificarToken, async (req, res) => {
    const { id_usuario } = req.query;
    try {
        const { data, error } = await supabase
            .from("notificaciones")
            .select("*")
            .eq("id_usuario", id_usuario)
            .order("fecha_notificacion", { ascending: false })
            .limit(20);
        if (error) throw error;
        res.status(200).json(data);
    } catch (error) {
        res.status(500).json({ error: error.message });
    }
});
```

```javascript
    const { tipo_solicitud, id_usuario } = req.body;
    try {
        // 1. Verificar solicitud pendiente existente
        const { data: existente } = await supabase
            .from('solicitudes')
            .select('id_solicitud')
            .eq('id_usuario', id_usuario)
            .eq('estado_solicitud', 'Pendiente')
            .maybeSingle();


        if (existente) {
            return res.status(400).json({ error: 'Ya tienes una solicitud pendiente.' });
        }


        // 2. Crear la solicitud
        const { data } = await supabase
            .from('solicitudes')
            .insert([{ tipo_solicitud, id_usuario, estado_solicitud: 'Pendiente' }])
            .select();


        // 3. Notificar a todos los admins
        const { data: admins } = await supabase
            .from('usuarios').select('id_usuario').eq('id_rol', 3);


        if (admins?.length > 0) {
            await supabase.from('notificaciones').insert(
                admins.map(a => ({
                    id_usuario: a.id_usuario,
                    asunto: `Alguien quiere ser artista`,
                    tipo_notificacion: 'Informativo',
                    fecha_notificacion: new Date().toISOString(),
                }))
            );
        }
        res.status(201).json({ mensaje: '¡Solicitud creada!', solicitud: data[0] });
    } catch (error) {
        res.status(500).json({ error: 'Error interno del servidor' });
    }
});
```


### 5.8 Middleware verificarToken


```javascript
// middlewares/verificarToken.js
import jwt from 'jsonwebtoken';


export const verificarToken = (req, res, next) => {
    const authHeader = req.headers['authorization'];
    const token = authHeader && authHeader.split(' ')[1]; // Bearer TOKEN


    if (!token) {
        return res.status(401).json({ mensaje: 'Acceso denegado. No hay token.' });
    }
    try {
        const decoded = jwt.verify(token, process.env.JWT_SECRET);
        req.usuario = decoded;
        next();
    } catch (error) {
        return res.status(403).json({ mensaje: 'Token inválido o expirado.' });
    }
};
```


### 5.9 Hook de React con paginación, `loading` y `error`


```javascript
import { useState, useEffect } from "react";


export function usePublicaciones(pagina = 1, porPagina = 12) {
  const [publicaciones, setPublicaciones] = useState([]);
  const [loading, setLoading]             = useState(true);
  const [error, setError]                 = useState(null);


  useEffect(() => {
    const cargar = async () => {
      setLoading(true);
      setError(null);
      try {
        const res = await fetch(
          `${import.meta.env.VITE_API_URL}/Muro-Publicaciones?pagina=${pagina}&limite=${porPagina}`
        );
        if (!res.ok) throw new Error("Error al cargar las publicaciones");
        setPublicaciones(await res.json());
      } catch (e) {
        setError(e.message);
      } finally {
        setLoading(false);
      }
    };
    cargar();
  }, [pagina, porPagina]);


  return { publicaciones, loading, error };
}
```

## 6. SEGURIDAD


### 6.1 Autenticación y autorización
- **Autenticación:** correo y contraseña; el backend entrega un token JWT firmado.
- **Autorización (RBAC):** el campo `id_rol` define los permisos. El middleware `verificarToken` valida el rol antes de ejecutar la operación.
- **Principio clave:** ocultar un botón en React **no** es seguridad. La validación real ocurre en el backend.

### 6.3 Contraseñas
Las contraseñas se almacenan con **bcrypt** (hash con sal y costo configurable), no en texto plano.


```javascript
const saltRounds = 10;
const hashedPassword = await bcrypt.hash(clave, saltRounds);
```


### 6.4 Row Level Security (RLS)
El backend accede a Supabase con la `service_role key`, por lo que la autorización principal está en los middlewares. Como defensa adicional se activa RLS:


```sql
ALTER TABLE usuarios       ENABLE ROW LEVEL SECURITY;
ALTER TABLE publicaciones  ENABLE ROW LEVEL SECURITY;
ALTER TABLE notificaciones ENABLE ROW LEVEL SECURITY;
-- Sin políticas para el rol anon: nadie puede leer o escribir
-- directamente con la clave pública. El backend usa la service_role key.
```

## 7. RENDIMIENTO Y OPTIMIZACIÓN


### Técnicas implementadas


**1. Límite de registros en notificaciones**
```javascript
// Solo se traen las últimas 20 notificaciones por petición
.limit(20)
```


**2. Badge sin consultas repetidas**
El badge no hace una petición al backend en cada render. Usa `SharedPreferences` (móvil) o estado local (web) para guardar la última vez que se abrió el panel, y solo cuenta las notificaciones más nuevas que esa fecha.


**3. Notificaciones no bloquean la acción principal**
El `try/catch` de `_notificarLike` y `_notificarComentario` (app móvil) está vacío a propósito — si la notificación falla, el like o comentario igual se guarda.


```dart
Future<void> _notificarLike(...) async {
  try {
    await http.post(...);
  } catch (e) {
    // No interrumpe el flujo si la notificación falla
  }
}
```


**4. Debounce en el buscador**
```javascript
export function useDebounce(valor, retraso = 300) {
  const [debounced, setDebounced] = useState(valor);
  useEffect(() => {
    const t = setTimeout(() => setDebounced(valor), retraso);
    return () => clearTimeout(t);
  }, [valor, retraso]);
  return debounced;
}
```
Sin esto, se haría una consulta por cada letra escrita. Con 300 ms de espera, "ArteNauta" (9 letras) genera **1 consulta** en vez de 9.

| **Error Boundary** | Evita que un fallo en un componente deje la pantalla en blanco |


```javascript
// ErrorBoundary.jsx
import { Component } from "react";


export class ErrorBoundary extends Component {
  state = { hayError: false };


  static getDerivedStateFromError() {
    return { hayError: true };
  }


  componentDidCatch(error, info) {
    console.error("Error capturado:", error, info);
  }


  render() {
    return this.state.hayError
      ? <p>Algo salió mal. Recarga la página.</p>
      : this.props.children;
  }
}
```
